# Flutter Industry-Level Optimization Checklist

Before building, modifying, or reviewing any Flutter application, follow these principles:

## 1. Architecture

* Use a scalable, modular architecture.
* Separate UI, state management, business logic, repositories, and data sources.
* Keep API/database logic out of widgets.
* Follow SOLID principles where appropriate.
* Use dependency injection where it improves testability and maintainability.
* Keep features modular and independently maintainable.
* Avoid unnecessary abstraction and over-engineering.
* Design the architecture to support testing, caching, offline behavior, and future scaling.

## 2. Widget Performance

* Use `const` widgets wherever possible.
* Keep widget trees reasonably small.
* Avoid unnecessary widget nesting.
* Keep `build()` methods lightweight.
* Never perform expensive calculations inside `build()`.
* Avoid unnecessary object creation during rebuilds.
* Break large widgets into smaller widgets.
* Rebuild only the smallest portion of the UI that needs updating.
* Use keys appropriately when widgets require identity preservation.

## 3. State Management

* Use an appropriate state-management solution consistently.
* Avoid watching/subscribing to unnecessarily large pieces of state.
* Prefer fine-grained state subscriptions.
* Avoid rebuilding entire screens when only one component changes.
* Keep business logic outside UI widgets.
* Avoid unnecessary global state.
* Dispose state/listeners/resources correctly.
* Keep transient UI state separate from application/business state.

## 4. List Performance

* Use `ListView.builder` / `GridView.builder` for large or dynamic collections.
* Never render thousands of items simultaneously when lazy loading is possible.
* Use pagination for large datasets.
* Prefer cursor-based pagination for very large datasets where appropriate.
* Avoid unnecessary `shrinkWrap`.
* Avoid nested scroll views unless required.
* Keep individual list items lightweight.
* Avoid expensive calculations for every list item during rebuilds.
* Use stable keys where appropriate.
* Optimize images inside lists.
* Avoid loading the entire dataset into memory unnecessarily.

## 5. Image Optimization

* Never load unnecessarily high-resolution images.
* Request appropriately sized images from the backend/CDN.
* Use thumbnails for lists and previews.
* Use WebP/AVIF where appropriate.
* Compress images.
* Use caching appropriately.
* Lazy-load images.
* Use placeholders for remote images.
* Use `cacheWidth`/appropriate decoding dimensions when useful.
* Avoid keeping large numbers of decoded images in memory.
* Optimize image loading specifically for low-end devices.

## 6. Memory Management

* Dispose controllers properly.
* Dispose `AnimationController`.
* Dispose `TextEditingController`.
* Dispose `ScrollController`.
* Dispose `FocusNode`.
* Cancel `StreamSubscription`s.
* Cancel timers when no longer required.
* Remove listeners when appropriate.
* Avoid memory leaks.
* Avoid unbounded caches.
* Avoid storing unnecessarily large objects globally.
* Avoid retaining entire datasets when only a subset is required.
* Monitor memory usage using Flutter DevTools.

## 7. CPU / Heavy Computation

* Never perform heavy synchronous work on the UI isolate.
* Identify CPU-intensive operations.
* Use isolates for genuinely expensive CPU-bound work.
* Consider `compute()` for suitable background parsing/transformation tasks.
* Move large JSON parsing away from the UI isolate when necessary.
* Move expensive encryption/compression/data processing away from the UI isolate when appropriate.
* Don't use isolates unnecessarily because they have overhead.

## 8. UI Rendering

* Minimize unnecessary rebuilds.
* Minimize expensive layout operations.
* Minimize unnecessary repaints.
* Use `RepaintBoundary` where profiling shows it is beneficial.
* Avoid excessive clipping.
* Avoid unnecessary opacity layers.
* Avoid unnecessarily complex shadows/effects.
* Be careful with large blur effects.
* Optimize custom painting when used.
* Profile rendering instead of guessing.

## 9. Animation

* Keep animations lightweight.
* Avoid expensive work during every animation frame.
* Use `AnimatedBuilder` when appropriate.
* Use implicit animations when they are sufficient.
* Avoid rebuilding large widget trees for small animations.
* Isolate expensive animated regions when appropriate.
* Test animations on low-end devices.
* Ensure animations remain smooth under realistic workloads.

## 10. Network Optimization

* Minimize unnecessary API requests.
* Use pagination.
* Use caching.
* Use request deduplication where appropriate.
* Use request cancellation where appropriate.
* Debounce search/input requests.
* Avoid sending duplicate requests.
* Compress network payloads.
* Keep JSON responses reasonably small.
* Request only the data actually needed.
* Use CDN infrastructure for large/static assets.
* Optimize remote images through resizing/CDN transformations.
* Implement appropriate retry and timeout policies.
* Handle poor network conditions gracefully.
* Support offline behavior where the product requires it.

## 11. API Design

* Avoid unnecessarily large API responses.
* Don't return fields the client doesn't need.
* Support pagination.
* Support filtering and sorting server-side when appropriate.
* Use appropriate caching headers.
* Use efficient serialization.
* Avoid N+1 API request patterns.
* Batch requests when appropriate.
* Design APIs with mobile bandwidth and latency in mind.

## 12. Database Optimization

* Don't load the entire database into memory.
* Query only required fields.
* Use pagination for large datasets.
* Add indexes to frequently queried fields.
* Avoid unnecessary database queries.
* Batch database operations where appropriate.
* Use transactions for related writes.
* Avoid querying the database from `build()`.
* Cache frequently accessed data when appropriate.
* Move expensive database operations away from UI rendering.
* Design local storage around actual access patterns.

## 13. Caching

* Cache data that is expensive or unnecessary to repeatedly fetch.
* Use appropriate cache expiration policies.
* Avoid unlimited caching.
* Cache images appropriately.
* Cache API responses where appropriate.
* Use local persistence for data that should survive app restarts.
* Define clear cache invalidation rules.
* Avoid stale data when freshness is important.
* Don't cache everything blindly.

## 14. Startup Performance

* Optimize time to first frame.
* Keep startup initialization minimal.
* Don't initialize every service before showing the first screen.
* Defer non-critical initialization.
* Avoid unnecessary synchronous startup work.
* Delay analytics/non-critical SDK initialization when appropriate.
* Delay non-critical API calls.
* Avoid loading large datasets during startup.
* Measure cold-start and warm-start performance.

## 15. Navigation

* Avoid unnecessarily expensive screen initialization.
* Don't reload expensive data every time a screen becomes visible unless required.
* Preserve state where appropriate.
* Use an appropriate navigation architecture.
* Avoid excessive navigation stack complexity.
* Keep navigation logic separate from business logic.

## 16. App Size

* Remove unused assets.
* Remove unnecessary dependencies.
* Audit transitive dependencies.
* Compress assets.
* Avoid shipping unnecessary fonts/files.
* Use release builds for size analysis.
* Use Android App Bundles where appropriate.
* Use platform/ABI-specific optimization where appropriate.
* Review native dependencies because they can significantly increase application size.

## 17. Dependency Management

* Add packages only when they provide meaningful value.
* Prefer mature, maintained packages.
* Check package maintenance and compatibility.
* Avoid multiple packages solving the same problem.
* Minimize dependency count when practical.
* Regularly audit dependencies.
* Avoid dependencies that introduce unnecessary native overhead.
* Keep versions controlled and reproducible.

## 18. Async Programming

* Never block the UI thread unnecessarily.
* Use asynchronous APIs for I/O.
* Handle loading/error/success states properly.
* Avoid unnecessary sequential awaits when operations can safely run concurrently.
* Avoid unbounded concurrency.
* Cancel work that is no longer needed.
* Prevent race conditions in asynchronous operations.
* Handle lifecycle changes correctly.

## 19. Error Handling

* Handle network failures.
* Handle database failures.
* Handle malformed API responses.
* Handle timeouts.
* Handle authentication expiration.
* Handle unexpected states.
* Avoid silently swallowing errors.
* Log useful diagnostic information.
* Never expose sensitive information in production logs.
* Provide appropriate user-facing fallback states.

## 20. Security

* Never hardcode secrets/API keys that must remain private.
* Never store sensitive credentials insecurely.
* Use secure storage where appropriate.
* Use HTTPS.
* Validate server responses.
* Don't trust client-side validation alone.
* Avoid exposing sensitive data through logs.
* Review third-party dependencies for security risks.
* Follow platform security best practices.

## 21. Production Logging

* Don't leave excessive debug logging enabled in production.
* Use structured logging where appropriate.
* Log important failures and performance issues.
* Avoid logging passwords, tokens, personal information, or secrets.
* Use crash reporting and monitoring in production.
* Make logs useful for diagnosing real-world problems.

## 22. Testing

* Unit-test business logic.
* Test repositories/data sources.
* Test important state-management behavior.
* Add widget tests for important UI behavior.
* Add integration tests for critical user flows.
* Test error states.
* Test offline/poor-network scenarios where relevant.
* Test large datasets.
* Test low-end device scenarios.
* Test different screen sizes.
* Test release builds.

## 23. Accessibility

* Support screen readers.
* Provide semantic labels where necessary.
* Ensure sufficient color contrast.
* Don't rely solely on color to communicate information.
* Support appropriate text scaling.
* Make touch targets sufficiently large.
* Test accessibility on both Android and iOS.

## 24. Responsive Design

* Don't hardcode dimensions unnecessarily.
* Support different screen sizes.
* Support tablets where required.
* Handle landscape mode where required.
* Avoid assuming a particular device resolution.
* Use adaptive layouts.
* Test unusual aspect ratios.
* Consider foldables/large screens when relevant to the product.

## 25. Offline / Poor Network Behavior

* Define what the application should do without connectivity.
* Cache important data.
* Display meaningful offline states.
* Avoid endlessly retrying requests.
* Queue operations when the product requires offline synchronization.
* Resolve synchronization conflicts appropriately.
* Make network failures recoverable.

## 26. Performance Profiling

Never optimize based purely on assumptions.

Use Flutter DevTools to inspect:

* CPU usage
* memory usage
* widget rebuilds
* rendering performance
* frame times
* network activity
* expensive functions
* allocations
* garbage collection
* startup performance

Follow:

```text
Identify problem
      ↓
Measure
      ↓
Find bottleneck
      ↓
Optimize
      ↓
Measure again
```

## 27. Build Configuration

* Never judge production performance exclusively from debug mode.
* Use profile mode for performance investigation.
* Use release builds for final performance validation.
* Test on physical devices.
* Test on lower-end hardware.
* Validate Android and iOS separately.
* Keep development/debug tooling out of production paths where appropriate.

## 28. UI/UX Performance

The application should feel fast, not merely benchmark fast.

Optimize:

* startup
* navigation
* scrolling
* search
* form interactions
* image loading
* API response handling
* animations
* loading states
* error recovery

Use skeletons/placeholders where appropriate instead of showing blank screens during expected loading.

## 29. Production Monitoring

After deployment, performance optimization doesn't stop.

Monitor:

* crash rate
* ANRs
* startup time
* API latency
* network failures
* memory issues
* battery impact
* user-facing performance
* slow screens
* backend errors

Use real production data to identify optimization opportunities.

## 30. General Rule

Before implementing any feature, ask:

```text
1. Will this cause unnecessary rebuilds?
2. Will this increase memory usage?
3. Is this CPU-intensive?
4. Is this doing unnecessary network work?
5. Is this doing unnecessary database work?
6. Can this be lazy-loaded?
7. Can this be cached?
8. Can this be paginated?
9. Can this work happen asynchronously?
10. Does this need to happen immediately?
11. Will this scale to 10x the current data?
12. Will this work on a low-end device?
13. Will this work on slow networks?
14. Does this increase app size?
15. Does this introduce an unnecessary dependency?
16. Is this secure?
17. Is this testable?
18. Is this accessible?
19. Is this responsive across screen sizes?
20. Can I measure and verify the performance impact?
```

### The master rule for AI

When you give this to an AI before building a Flutter application, tell it:

> **Before implementing any feature, review the entire application against this optimization checklist. Do not optimize blindly. Prefer measurable, scalable, maintainable solutions. Consider UI rendering, rebuilds, state management, memory, CPU, isolates, networking, API design, database performance, caching, images, startup time, app size, dependencies, security, accessibility, testing, responsive design, and production monitoring. For every significant architectural or performance decision, explain the trade-offs and choose the solution appropriate for a production-scale Flutter application.**

That gives you a much better **“production-first Flutter” baseline** than simply telling an AI to “write optimized Flutter code.”
