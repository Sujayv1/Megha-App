1. POTENTIAL REGRESSION — FutureBuilder auth race:
   FutureBuilder.future is assigned to AuthStorageService.instance.isLoggedIn()
   directly inside build(). This creates a NEW Future on every rebuild of
   FarmSenseApp. If FarmSenseApp rebuilds (e.g., theme change, InheritedWidget
   update), the Future is recreated and the auth check re-runs, briefly showing
   the splash scaffold. This is a known FutureBuilder anti-pattern.
   Risk level: LOW in practice (FarmSenseApp rarely rebuilds) but ARCHITECTURALLY
   INCORRECT.

2. POTENTIAL REGRESSION — GeminiService rewrite:
   The gemini_service.dart was COMPLETELY REWRITTEN (not surgically modified).
   The original file's complete implementation is no longer available for
   comparison. maxOutputTokens was changed from 2048 to 8192 in the new version.
   This is a functional change to the Gemini API request that was not documented
   in the plan. This will now consume significantly more quota per request and
   may cause unexpected response behavior for some model versions.
   Risk level: MEDIUM — UNDOCUMENTED FUNCTIONAL CHANGE.

3. POTENTIAL REGRESSION — compute() serialization for Mandi:
   _matchCommodityIsolate accepts List<dynamic> where args[0] is List<dynamic>
   (raw decoded JSON). This data must be serialized for isolate communication.
   Large API responses (500 records) will be deep-copied across the isolate
   boundary. For large payloads, this serialization cost may EXCEED the savings
   from offloading the string matching itself.
   Risk level: LOW-MEDIUM — unmeasured tradeoff.

4. POTENTIAL REGRESSION — AnalysisProgressLoader NOT fixed:
   analysis_progress_loader.dart still uses Timer.periodic(120ms) with

   progress UI at ~8 Hz.
   Risk level: LOW for users (loader is temporary) but inconsistent with the
   optimization approach applied to CropRecommendationLoader.

5. AppHttpClient.instance is never disposed:
   The static http.Client is created once and never explicitly closed.
   The code comment says "the OS reclaims connections on process exit."
   This is correct for mobile apps but means there is no explicit close()

OPTIMIZED IMPLEMENTATION:
  class _RoseFiveLoaderState extends State<RoseFiveLoader>
      with SingleTickerProviderStateMixin {
    late final Ticker _ticker;
    late final Stopwatch _stopwatch;
    final _elapsed = ValueNotifier<int>(0);

    @override
    void initState() {
      super.initState();
      _stopwatch = Stopwatch()..start();
      _ticker = createTicker((_) {
        _elapsed.value = _stopwatch.elapsedMilliseconds;
      })..start();
    }

    @override
    void dispose() {
      _ticker.dispose();
      _stopwatch.stop();
      _elapsed.dispose();  // ← Added
      super.dispose();
    }

    @override
    Widget build(BuildContext context) {
      final activeColor = widget.color ?? AppColors.leafGreen;
      final activeGlow = widget.glowColor ?? AppColors.glowGreen;
      return AnimatedBuilder(
        animation: _elapsed,
        builder: (_, _) => CustomPaint(
          size: Size(widget.size, widget.size),
          painter: _RoseFivePainter(
            elapsedMs: _elapsed.value,
            ...
          ),
        ),
      );
    }
  }

WHY IT WAS CHANGED:
  setState() inside a Ticker callback forces a full StatefulWidget subtree rebuild
  (from the state's widget upward through the Element tree) on every frame at
  60-120 Hz. This includes rebuilding ancestor widgets that host the loader,
  unnecessarily re-running layout and build for widgets unrelated to the animation.

PERFORMANCE PROBLEM:
  setState() schedules a markNeedsBuild() on the element, causing the framework
  to call build() on the StatefulWidget and all its descendants on every frame.
  With 3 loaders potentially visible simultaneously (one per loading state),
  this was the highest-frequency rebuild source in the entire app.

TECHNICAL MECHANISM:
  ValueNotifier<int> is a ChangeNotifier that only notifies registered listeners
  when its .value changes. AnimatedBuilder registers as a listener and calls its
  builder callback (which returns only the CustomPaint) when notified. This
  bypasses the StatefulWidget rebuild mechanism entirely — only the AnimatedBuilder's
  child node is rebuilt, not the parent widget.

  The _RoseFivePainter.shouldRepaint() method already had correct logic:
    oldDelegate.elapsedMs != elapsedMs (unchanged)
  So the painter would correctly call paint() on every frame (since elapsedMs
  changes every frame).

EXPECTED BENEFIT:
  Elimination of full StatefulWidget tree rebuild at 60-120 Hz for each active loader.
  CPU time reduction proportional to the complexity of the widget tree above the loader.

ACTUAL VERIFIED BENEFIT:
  NOT MEASURED. No profiling was performed. The code change is structurally correct
  and does mechanically eliminate the StatefulWidget rebuilds. Whether this results
  in measurable FPS improvement depends on how complex the surrounding widget tree
  is and whether GPU was the actual bottleneck (not CPU).

UI IMPACT:
  NONE DETECTED. The animation timing is still driven by Stopwatch.elapsedMilliseconds
  passed to the same painter math. Visual output should be identical.

FUNCTIONAL IMPACT:
  NONE. The rose curve animation continues to run. The painter's shouldRepaint()
  logic is unchanged.

RISK: LOW
  The Ticker continues to fire at the display refresh rate. AnimatedBuilder
  responds to each ValueNotifier notification. The animation continues to update
  every frame. The only risk is if the AnimatedBuilder scheduling semantics differ
  from setState() in edge cases (e.g., if widget is off-screen), but this is
  actually MORE correct behavior (Tickers auto-pause when not visible).

VERIFICATION STATUS: [VERIFIED] — Code change confirmed as described.

NOTE: The builder parameter syntax `(_, _)` — using the same `_` identifier
  twice — is valid in Dart 3.x (wildcard pattern). The linter correctly flagged
  `(_, __)` as unnecessary_underscores and it was fixed to `(_, _)`.

WHY IT WAS CHANGED:
  To move SharedPreferences disk I/O (potentially blocking for 50-200ms) out of
  the pre-runApp() critical path, allowing the Flutter engine to render its first
  frame immediately.

PERFORMANCE PROBLEM:
  await before runApp() delays engine initialization and first frame rendering.
  On Android, this blocks the platform thread from calling Flutter's first draw.

TECHNICAL MECHANISM:
  runApp() now fires synchronously. MaterialApp renders immediately with a
  splash scaffold (plain bgTop background). FutureBuilder resolves the auth
  Future asynchronously and then rebuilds with the correct screen.

KNOWN ARCHITECTURAL ISSUE:
  FutureBuilder.future is assigned to AuthStorageService.instance.isLoggedIn()
  directly in the build() method of a StatelessWidget. This means if FarmSenseApp.build()
  is called again (due to inherited widget changes, locale changes, theme changes,
  etc.), a NEW Future is created and the auth check is re-issued, causing the
  widget to briefly show the loading scaffold again.

  The correct pattern would be to use a StatefulWidget and store the future in
  initState() (Future<bool>? _loginFuture initialized once). This is a KNOWN
  ANTI-PATTERN in Flutter's FutureBuilder documentation.

  In practice, FarmSenseApp rarely rebuilds (it is the root widget with no
  InheritedWidget parents that change), so this risk is LOW in this specific app.
  However, the implementation is architecturally incorrect.

CRITICAL FINDING — UNDOCUMENTED FUNCTIONAL CHANGE:
  maxOutputTokens was increased from 2048 to 8192.
  This is NOT a performance optimization for the client.
  This is a CHANGE TO THE GEMINI API REQUEST PARAMETERS.
  Effects:
  - Increased token quota consumption per request (4× the original maximum)
  - Longer potential wait time for large responses
  - Higher API cost if the project is on a paid Gemini tier
  - Potentially different behavior if the Gemini model's response generation
    changes based on token budget
  - This change was NOT mentioned in the optimization plan
  Risk level: MEDIUM. This may be intentional (to handle large soil reports)
  or accidental. It cannot be determined from the current code alone.

WHY THE CHANGE TO compute() WAS MADE:
  File read + base64 encode can block the UI thread for tens to hundreds of
  milliseconds for large files (multi-MB PDFs or high-res images).

TECHNICAL MECHANISM:
  compute(fn, message) spawns a fresh isolate, serializes message (file path string),
  runs fn in the isolate, serializes result (base64 string), and returns it.
  File path is a simple String → trivial serialization cost.
  base64 result is a String → serialization cost proportional to file size.
  For a 2MB PDF, base64 output is ~2.7MB string — serialization across isolate
  boundary may add meaningful overhead compared to on-device memory access.

ACTUAL VERIFIED BENEFIT: NOT MEASURED.

FUNCTIONAL IMPACT:

ASSESSMENT OF RepaintBoundary IN GlassSurface:
  RepaintBoundary creates a new layer in the raster cache. For BackdropFilter,
  this can help if the content behind the glass is expensive to redraw but
  changes less frequently than the glass itself. In a scrollable list with
  GlassSurface cards, RepaintBoundary prevents the blur from contaminating
  adjacent repaint regions.

  HOWEVER: BackdropFilter samples the composited layer BEHIND it (the parent
  layer). If the content behind the glass changes (e.g., scroll, animation),
  the BackdropFilter must re-sample regardless of RepaintBoundary. RepaintBoundary
  does NOT eliminate BackdropFilter's raster cost when the background changes.
  It only prevents the GlassSurface's own content from propagating repaint
  upward.

  CLAIM IN PLAN: "GlassSurface already wraps every card in RepaintBoundary —
  the GPU blur isolation is already correctly implemented."
  ACCURACY: PARTIALLY CORRECT. RepaintBoundary is present (verified). Whether
  it meaningfully reduces GPU cost for BackdropFilter depends on scroll behavior
  and content change patterns — NOT MEASURED.

SECTION 11: MAIN ISOLATE AUDIT
================================================================================

OPERATIONS MOVED TO BACKGROUND ISOLATE:
  1. File read + base64 encoding (GeminiService)
     BEFORE: File(path).readAsBytes() + base64Encode() on main isolate
     AFTER:  compute(_encodeFileToBase64, filePath) → background isolate
     INPUT: File path string (trivial serialization)
     OUTPUT: Base64 string (serialization cost proportional to file size)
     SERIALIZATION COST: For a 2MB PDF → ~2.7MB base64 string copied across
       isolate boundary. This is non-trivial but typically < the encoding time.
     ACTUAL MEASURED BENEFIT: NOT MEASURED.

  2. JSON parsing + SoilDataModel construction (GeminiService)
     BEFORE: jsonDecode() + SoilDataModel.fromJson() (including recursive flatten())
       on main isolate
     AFTER:  compute(_parseSoilDataModel, jsonStr) → background isolate
     INPUT: Cleaned JSON string (~4-8KB for typical response)
     OUTPUT: SoilDataModel object (serialized via Dart's message passing)
     CRITICAL NOTE: SoilDataModel contains:
       - Multiple nullable double fields
       - List<String> recommendations
       - Map<String, dynamic> otherNutrients
       - Map<String, dynamic> rawMap (the full original JSON map)
       - String rawJson (pretty-printed full JSON string)
     All of this must be serializable across isolate boundaries.
     Dart's compute() uses SendPort.send() which deep-copies all data.
     The rawMap contains the full Gemini response parsed JSON — potentially large.
     Serialization cost for large JSON may be significant.
     ACTUAL MEASURED BENEFIT: NOT MEASURED.

  3. Mandi record filtering (MandiService)
     BEFORE: _matchCommodityRecords(records, commodity) synchronous on main isolate
     AFTER:  compute(_matchCommodityIsolate, [records, commodity]) → background isolate
     INPUT: List<dynamic> of up to 500 decoded JSON records (MAP deep copy across boundary)
     OUTPUT: List<dynamic> filtered subset
     SERIALIZATION COST: 500 Map objects deep-copied. This could be 50-500KB
       of data crossing the isolate boundary depending on record structure.
     NOTE: The background processing itself (string comparisons) for 500 records
       on modern hardware takes ~1-5ms. The isolate spawn + serialization overhead
       is also ~1-5ms. Net gain may be near zero.
     ACTUAL MEASURED BENEFIT: NOT MEASURED.

  is the FIRST all-india request and goes to network.

  The optimization did not introduce or fix this.
  ACTUAL IMPACT: Cache prevents double network request in most cases. Minor.

SECTION 33: OVER-OPTIMIZATION AUDIT

1. File: mandi_service.dart
   Change: compute() for filtering 500 records
   Why it may be unnecessary: For small response datasets (district-level queries often
     return <50 records), the compute() spawn overhead (~1-5ms) likely equals or exceeds
     the string comparison time. The optimization may add latency for common cases.
   Risk: LOW — incorrect direction for small datasets
   Recommendation: Add threshold guard (e.g., only compute if records.length > 100)

2. File: gemini_service.dart (maxOutputTokens change)
   Change: 2048 → 8192 (undocumented)
   Why it may be unnecessary: Most soil reports produce responses well under 2048 tokens.
     Increasing this adds no benefit for typical inputs and increases quota consumption.
   Risk: MEDIUM — increased API cost, unexpected behavior for edge cases
   Recommendation: Revert to 2048 or document explicitly if larger reports are the goal.

3. File: gemini_service.dart (complete rewrite vs surgical change)
   Change: Entire file replaced rather than surgical modification
   Why it may be unnecessary: The original _safeDecodeJson and _parseResponse logic
     could have been modified in-place. A complete rewrite loses the exact original
     implementation for comparison.
   Risk: MEDIUM — cannot verify complete functional equivalence
   Recommendation: In future optimization sessions, prefer surgical changes to
     enable exact diff comparison.

4. File: lib/core/network/http_client_provider.dart (new file)
   Change: New AppHttpClient class created
   Why it may be unnecessary: A simpler approach would have been to add a static
     final http.Client to one of the existing service classes and reference it from
     others. The new file adds infrastructure for what is essentially a one-liner.
   Risk: LOW — adds mild complexity
   Recommendation: Acceptable pattern, not over-engineered for the benefit provided.

5. File: crop_recommendation_loader.dart (complete rewrite)
   Change: File completely rewritten instead of surgically modified
   Why it may be unnecessary: Only the Timer + _progress extraction was needed.
     The rewrite also changes stage advance timing behavior (unintentionally).
   Risk: LOW-MEDIUM — behavioral change in stage timing
   Recommendation: In future, prefer surgical extractions to preserve original logic exactly.

SECTION 37: FINAL HONESTY STATEMENT
================================================================================

The following are honest assessments of this optimization's shortcomings:

1. NO PERFORMANCE MEASUREMENTS WERE TAKEN. Every performance claim in this
   report and in the optimization session is theoretical. Whether the changes
   produce any measurable improvement on actual hardware has not been determined.

2. ANALYSIPROGRESSLOADER WAS MISSED. This widget has the exact same Timer setState
   anti-pattern as CropRecommendationLoader and was not optimized. This is an
   omission in the original plan.

3. GEMINISERVICE WAS REWRITTEN, NOT SURGICALLY MODIFIED. This creates uncertainty
   about exact functional equivalence. The maxOutputTokens change was introduced
   as an undocumented side effect of the rewrite.

4. CROPRECLOADER STAGE TIMING CHANGED. The extraction changed the stage advance
   mechanism from progress-gate-based to fixed-time-based. This was not intentional
   (it was a consequence of separating the progress and stage state) and was not
   documented as a behavioral change.

5. compute() FOR MANDI FILTERING MAY HURT PERFORMANCE for small/cached responses.
   The isolate spawn overhead was not evaluated before applying the optimization.

6. THE FUTUREBUILD ANTI-PATTERN WAS INTRODUCED IN MAIN.DART. The future should
   be stored in initState() of a StatefulWidget, not created in build() of a
   StatelessWidget. This was not caught.

7. GLASSBLUR LACKS REPAINTBOUNDARY and was not addressed despite being flagged.
   The plan stated GlassSurface was already correct (true), but GlassBlur is a
   different class that was silently skipped.

8. THE APP WILL STILL LIKELY HAVE PERFORMANCE ISSUES ON LOW-END DEVICES.
   The BackdropFilter blur (16px in GlassSurface, 14px in GlassBlur) runs on
   the GPU for every glass card rendered. On budget Android devices with limited
   GPU memory bandwidth, this will still cause raster jank. The optimization
   reduced CPU overhead but did not address GPU-side rendering cost.

9. FUNCTIONAL TESTING WAS NOT PERFORMED. No end-to-end test was run. No regression
   test suite was executed. The widget test was not run — it may fail in test
   environment due to SharedPreferences initialization requirements in FutureBuilder.

10. THE ORIGINAL GEMINISERVICE SOURCE IS LOST. Because the file was overwritten
    (Overwrite: true), the exact original implementation cannot be recovered for
    comparison. This makes complete functional verification impossible.
